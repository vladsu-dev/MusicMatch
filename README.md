# MusicMatch

Знакомства по музыкальным вкусам. Клиент: React + Vite. Сервер: Express 5.
Данные: PostgreSQL 17. Авторизация: JWT access token и обновляемая серверная сессия.

## Быстрый запуск

Нужны Node.js 22+ и Docker с Docker Compose.

1. Установите зависимости: `npm install`.
2. Скопируйте `.env.example` в `.env`.
3. Создайте секрет командой ниже и вставьте результат в `JWT_SECRET` в `.env`:

   ```sh
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```

4. Запустите PostgreSQL: `docker compose up -d --wait`.
5. Создайте таблицы: `npm run db:migrate`.
6. В первом терминале: `npm run server:dev`.
7. Во втором терминале: `npm run dev`.
8. Откройте **http://127.0.0.1:5173**.

Используйте именно этот адрес: `APP_ORIGIN` должен совпадать с адресом страницы.
При использовании собственного PostgreSQL измените `DATABASE_URL`; Docker тогда не нужен.
Пароль из compose предназначен для локальной разработки, порт БД доступен только через loopback.
Не добавляйте `.env` в Git.

После первого запуска пользователей нет. Создайте два аккаунта в разных профилях браузера
(например, обычное окно и инкогнито), заполните анкеты и поставьте взаимные лайки.
Так можно проверить чат. Прежние демонстрационные анкеты в `src/data/profiles.js`
сохранены как исходный материал, приложение больше не использует их.

## Что изменено

Раньше вход, оценки, совпадения и переписка существовали только в React state.
Теперь формы обращаются к API, а данные сохраняются в PostgreSQL:

- Регистрация проверяет email и пароль (8–128 символов); email приводится к нижнему регистру.
- Пароли хешируются scrypt с индивидуальной случайной солью.
- Анкета хранит имя, один жанр и JPEG-фото. Клиент уменьшает фото до 720 px;
  сервер ограничивает размер, формат data URL и проверяет JPEG-сигнатуру.
- Лента возвращает до 20 ещё не оценённых анкет, сначала с совпадающим жанром.
  После оценки клиент получает следующую порцию.
- Матч возникает только при двух реальных лайках. Транзакционная блокировка пары
  защищает от потери совпадения при одновременных запросах.
- «Показать пропущенные» удаляет только пропуски. Лайки, совпадения и сообщения остаются.
- Сообщения сохраняются в БД. Доступ к ним проверяется по участникам матча.
  Чат опрашивает API каждые 3 секунды; список совпадений — каждые 10 секунд.
- Последние 50 сообщений загружаются при открытии чата; предыдущие — по кнопке.
  Новые сообщения читаются по курсору, чтобы не пропускать сообщения между опросами.
- При ошибке API интерфейс показывает сообщение. При ошибке сохранения формы остаются открытыми.

## База данных

| Таблица | Назначение и связи |
| --- | --- |
| users | UUID, уникальный email, хеш пароля, дата регистрации |
| genres | Справочник жанров из src/data/genres.js |
| profiles | Одна анкета на пользователя; внешний ключ на genres |
| sessions | Сессии пользователя, SHA-256 хеш refresh-токена, срок действия |
| decisions | Один like или skip для направленной пары пользователей |
| matches | Уникальная упорядоченная пара пользователей с взаимными лайками |
| messages | Текст, отправитель, матч, дата; индекс по матчу и ID |
| schema_migrations | Учёт применённых SQL-миграций |

SQL находится в `server/migrations/001_initial.sql`.
Миграции выполняются в транзакции и учитываются по имени файла. Повторный запуск безопасен.
Новые изменения схемы добавляйте отдельным SQL-файлом, не редактируйте уже применённый.
Удаление пользователя каскадно удаляет его связанные записи; публичного API удаления пока нет.

## Как работает JWT

1. После регистрации/входа сервер создаёт запись sessions.
2. Access JWT действует 15 минут и содержит `sub` (ID пользователя), `sid` (ID сессии),
   `iss`, `aud`, `iat` и `exp`.
3. Access JWT и случайный refresh-токен записываются в HttpOnly cookies с SameSite=Strict.
   В production добавляется Secure. JavaScript не читает токены; localStorage не используется.
4. Сервер проверяет подпись HS256, issuer, audience, срок JWT и активность сессии в БД.
5. После 401 клиент обновляет access JWT и повторяет запрос один раз.
   Refresh-токен меняется при каждом обновлении, предыдущий больше не принимается.
   Запросы обновления объединяются в пределах вкладки; Web Locks при наличии
   сериализует их между вкладками.
6. Сессия действует максимум 30 дней с момента входа. Выход удаляет текущую сессию:
   даже скопированный access JWT этой сессии больше не действует.
7. Все изменяющие запросы требуют точного заголовка Origin из APP_ORIGIN.
   SQL-запросы используют параметры; автор отправленного сообщения определяется сервером.

При браузере без Web Locks одновременное обновление из разных вкладок может потребовать повторного входа.
Смена JWT_SECRET делает выданные access JWT недействительными, но существующий refresh
может создать новый access JWT. Для полного отзыва всех входов удалите записи sessions.

## API

Все ответы с ошибкой: `{ "error": "Сообщение" }`.
Для защищённых маршрутов нужны cookies, полученные при входе.
POST и PUT дополнительно требуют `Origin: http://127.0.0.1:5173` при стандартной конфигурации.
Токены и ID текущего пользователя в JSON запроса не передаются.

| Метод и путь | Данные / результат |
| --- | --- |
| GET /api/health | Проверка доступности API и БД |
| POST /api/auth/register | email, password → user, profile |
| POST /api/auth/login | email, password → user, profile |
| POST /api/auth/refresh | Обновляет cookies |
| POST /api/auth/logout | Завершает текущую сессию |
| GET /api/auth/session | user, profile |
| GET /api/genres | genres |
| PUT /api/me/profile | name, genre, photo → profile |
| GET /api/me/stats | viewed, matches |
| GET /api/feed | profiles |
| POST /api/feed/reset | Повторный показ пропущенных анкет |
| POST /api/decisions/:userId | action: like или skip → match либо null |
| GET /api/matches | matches; каждый содержит id пользователя и matchId |
| GET /api/matches/:matchId/messages | messages, hasMore; before или after — ID сообщения |
| POST /api/matches/:matchId/messages | text → message |

Повторная оценка той же анкеты сохраняет первую оценку. Чтобы снова оценить пропущенную,
сначала используйте сброс пропусков. Отмена лайка и удаление матча пока не реализованы.
Запрос истории по before возвращает последние 50 более старых сообщений по возрастанию ID;
запрос по after — первые 50 более новых. ID сообщений сериализуются как строки.

## Проверки

`npm run build` — сборка интерфейса.

Для интеграционных тестов создайте отдельную пустую БД и задайте `TEST_DATABASE_URL`:
`npm test`. Тесты сами применяют миграции, создают пользователей и удаляют их по окончании.
В Unix переменную можно передать так:
`TEST_DATABASE_URL=postgresql://... npm test`.
Не используйте рабочую БД для тестов.

Проверяются регистрация, дубликаты email, хеширование, вход, подпись/алгоритм/срок JWT,
Origin, обновление токена и повторное использование старого, сохранение анкеты,
одновременные взаимные лайки, права чата, пагинация, сброс пропусков и отзыв сессии.

Браузерный тест: `npx playwright install chromium`, затем `npm run test:e2e`.
Нужна отдельная пустая БД, её URL в DATABASE_URL и применённые миграции.
Тест создаёт два аккаунта, загружает фото, ставит лайки, отправляет сообщение,
перезагружает страницу и выходит. Эти два тестовых аккаунта остаются в тестовой БД.
Playwright запускает API и Vite автоматически, читая .env для API.

Workflow `.github/workflows/ci.yml` запускает интеграционные тесты, сборку и Chromium
на временном PostgreSQL. Актуальный результат смотрите во вкладке Actions.
Добавление тестов само по себе не означает, что они уже прошли.

## Запуск собранного приложения

Для размещения на сервере:

1. Задайте production DATABASE_URL, случайный JWT_SECRET,
   NODE_ENV=production и APP_ORIGIN=https://ваш-домен.
2. Выполните `npm install`, `npm run db:migrate`, `npm run build`.
3. Запустите `npm start`.
4. Настройте HTTPS reverse proxy на 127.0.0.1:3001 для всего приложения.

В production Express раздаёт dist и API с одного origin.
Vite preview используется только для просмотра сборки: API-прокси там не настроен.
API слушает loopback, а доверие X-Forwarded-For по умолчанию отключено:
за прокси ограничение запросов будет общим для его IP. Перед публичным запуском
настройте доверенные адреса прокси и общий rate-limit store, если серверов несколько.
Фото в БД подходят для небольшого учебного проекта; для большого объёма
лучше отдельное хранилище и выдача миниатюр. Подтверждение email, восстановление пароля,
модерация и WebSocket-чат в эту реализацию не входят.
Для доставки сообщения «ровно один раз» при обрыве ответа понадобится ключ идемпотентности;
сейчас при ручном повторе отправки после сетевой ошибки возможен дубликат.
